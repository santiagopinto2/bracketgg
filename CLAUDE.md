# BracketGG

Angular viewer for start.gg brackets, live at https://bracket.santiagopinto.dev.

## start.gg API

- Before saying the API has or lacks something, look it up in `docs/startgg-schema.graphql`: the whole public schema, saved from introspection. Refresh it with `STARTGG_TOKEN=... node scripts/startgg-schema.mjs` and commit the diff.
- Things start.gg's website shows that the public API doesn't have: ranking series logos (`RankingSeries` isn't in the schema; `PlayerRank.images` is a different, often empty, image) and the event description.
- Query complexity counts the objects actually returned, about 1000 per request at most. A refusal message includes "(actual: N)", but N can be just the cap, "(actual: 1000)", when start.gg stops counting (a Melee Doubles Top 24 of 31 sets, 2026-11-14); then only halving the page helps (`nextPageSize`).
- Measured costs: a slimmed set is about 10 objects (with the phase id and games, no characters), games where none were reported cost 1 per set, full best of 5 character data is about 50 per set. A phase's players (`Phase.seeds` with each entrant's participants) cost about 3 per player; pictures (`images`) don't count. A connection costs what it returns, not its `perPage`, so lowering `SETS_PER_STANDING` (the top 8's "Lost to") saves nothing; `SetFilters` can't ask for only an entrant's losses. `extensions.queryComplexity` in start.gg's answer gives a query's count.
- Phase-level `sets` (any sortType: ROUND and NONE both measured) returns each pool's sets in the same order as asking per pool, but interleaves the pools (sorted by round across all of them), so every pool spans every page. Multi-pool phases therefore load as pool slices: aliased `phaseGroup(id) { sets(page, perPage) }` pages, several pools per request (`poolSlicesQuery`).
- From a pool, a set costs 9 objects (no characters reported) and each aliased `phaseGroup` 1, even when its page is empty (measured 2026-11-13).
- Progression (where a pool's players go in a later phase) is read from the next phase's seeds, not from the sets: `Phase.seeds { entrant { id } phaseGroup { id displayIdentifier } progressionSource { originPlacement originOrder originPhaseGroup { id } } }` (`phaseProgressionsQuery`) costs 4 objects per seed, 240 seeds a request (Genesis X R2 Pools' 384 seeds: 961 and 577; measured 2026-11-13). The bracket view asks it of each phase that names the shown phase in `Phase.progressingInData { origin }` (in `eventPhasesQuery`; filled in before an event starts), alongside the sets. `Set.winnerProgressionSeed` and `loserProgressionSeed` say the same per set but cost 2 objects on every set, so the set queries leave them out.
- Losers Round 1 of a double elimination pool can link (`prereqId`, placement 1) to sets start.gg never sends. Before a pool starts their ids say what they are: `preview_<pool>_-2_<k>` holds the loser of winners round 1 set `preview_<pool>_1_<k>`, and with byes `preview_<pool>_-3_<k>` is a Losers Round 1 bye holding whoever reaches it from `-2_<2k>` or `-2_<2k+1>`. In a started pool the ids are numbers in the same order. Show Projected maps them in `getHiddenLosersSources`; it matched start.gg's own Show Projected on every unstarted Port Priority DX Melee and Rivals II pool (2026-11-14).
- A pool can be seeded with no sets at all, not even preview ones (Port Priority DX Melee Singles E43, 2026-11-14), while start.gg's own page draws it from the seeds. Then `poolSeedsQuery` (`seedMap`, `progressionsOut`, and the seeds) gives what `generated-bracket.ts` builds the sets from, with start.gg's preview ids and round numbers; its projection matched start.gg's for E43. It builds only power-of-two pools without byes whose players all start there.
- A seed's `entrant` is null until start.gg places a player in it. A placed player's tag goes on their last set in the pool (found from the slots' `prereqId` links); an unplaced seed says only a placement, so the pool's exit sets get a tag with the phase's name. A player keeps their entrant id in every phase of an event, so a tag's link names them as `?player=<entrant id>`. Once the bracket has scrolled to them, the address drops `?player=` (and the `?set=` Back returns to) and the history entry keeps it (`arrival-state.ts`): Back and Forward still scroll there, a refresh opens at the top.
- The set dialog (`src/app/components/set/`) reads `state`, `totalGames`, `startedAt`, `completedAt` and `vodUrl` from the bracket's own set fields: scalars, which cost nothing (Genesis X top 8: 393 objects with and without them). `stream` costs 1 object for every set, streamed or not (measured 2026-11-14), so it isn't in the bracket's queries: the dialog asks for it when it opens, with the players' X and Twitch, in `setDetailsQuery` (18 objects for a singles set).
- Attendees (`/tournament/<slug>/attendees`): `Tournament.participants` sorts by `sortBy: "<column> asc"` for id, createdAt, checkedInAt, prefix, userId, and playerId, ignores other names, and returns nothing for "gamerTag asc". Its search (`filter.search`, `fieldsToSearch: ["gamerTag"]`) looks in tags only; a null `searchString` filters nothing, but `eventIds: [null]` matches nobody. A row's data costs about 11 objects per attendee (50 cost 555 at the top of Genesis X's list; measured 2026-11-14).
- Seed order comes only from `Phase.seeds` with `sortBy: "seedNum"`, spelled without a direction: the default order is the order the seeds were made, "seedNum asc" shuffles them, and `Event.entrants` can't be sorted by seed. The Attendees page uses the phase that holds every entrant, and falls back to the tournament's list (no seed order) for an event where no phase does. With the row data a singles seed costs up to 18 objects and a two-player team 32.
- An attendee's seeds and pools (`Participant.entrants.seeds`) cost 10 to 20 objects per event entered, so only the attendee dialog asks for them, one attendee per request (`attendeeDetailsQuery`). A variable sent to `/api/gql` can't be null (`server/gql-cache.js` takes plain values only): leave it out instead.
- The tournament page (`/tournament/<slug>`, `src/app/components/tournament/`; `tournament-view.ts` works out what it says) reads one `tournamentQuery`, which the menu and every other page share: Genesis X (30 events, 76 phases, 8 streams) costs 582 objects, about 19 per event with its top 3 and phases; without those (`tournamentLiteQuery`, the fallback when start.gg refuses the full one) it costs 133. Results' top 8s come from `tournamentResultsQuery`, asked only of the two biggest events with final results: 33 objects per singles event, 49 per two-player team event (measured 2026-11-15).
- `Tournament.state` stays 1 while its events are being played (The Roundtable 12, 2026-11-15), and an event can stay `CREATED` in a finished tournament (Genesis X's Classic Tetris). So the page reads "Live" from the events' states and the dates, and shows results only from standings that start at 1st and are final (`isFinal`, or the event is `COMPLETED`): before an event ends everyone still in shares one placement.
- An event's phases come in no useful order and `phaseOrder` can be wrong (Genesis X Melee Singles: R1 Pools 1, R2 Pools 5, Top 64 3, Top 8 4). `orderPhases` (`src/app/services/phase-order.ts`) sorts them by their progressions (`progressingInData`), then `phaseOrder`, with exhibitions (`isExhibition`, like Port Priority DX's Salmon Ladder, a matchmaking side bracket) last; `lastPhase` is the last one that isn't an exhibition. The service sorts every event's phases as they arrive.
- `Tournament.streams` is null when there are none. A stream's `streamName` is the Twitch channel; other sources' addresses aren't known, so only Twitch streams are links. start.gg's map of the venue isn't in the API (`lat`, `lng`, and `mapsPlaceId` only), and the page draws none.
- All queries go through the site's own cache, `POST /api/gql` (`server/gql-cache.js`), via `src/app/services/startgg.service.ts`.
- Query texts live in `src/app/services/startgg-queries.ts`, with GraphQL variables for slugs, ids and pages. The server runs only those exact texts (`server/gql-allowlist.js` loads the same file), so a new or changed query goes there and nowhere else.

## Server (`proxy-server.js`, `server/`)

- Logging in is optional. Visitors who aren't logged in are served with the site's own token (`STARTGG_SITE_TOKEN`), held to 70 requests a minute by `server/site-gate.js`; past that `/api/gql` answers 503 `SITE_BUSY` with Retry-After.
- Logged-in visitors' start.gg tokens stay on the server (`server/sessions.js`, saved to `SESSIONS_FILE`); the browser holds only the HttpOnly `bgg_session` cookie. `server/auth.js` refreshes tokens and ends a session only when start.gg refuses its refresh token.
- The cache (`server/gql-cache.js`) keeps an answer 15 s (sets), 1 minute (pools, progressions), or 5 minutes (the rest), and 6 hours when the answer says it's finished: every set in it `state` 3 (or a DQ with a winner), the event, every event, or the phase `COMPLETED`, or the tournament's `endAt` passed with every event completed, or a day past with none being played (`FINISHED`). Some queries ask for a `state` or `endAt` only for this. Anything else keeps the short time.
- The cache is saved to `GQL_CACHE_FILE` (default `gql-cache.json` next to `SESSIONS_FILE`) every 5 minutes and on SIGTERM, and loaded at start without expired answers; a bad file means starting empty. `GET /api/gql/stats` shows the totals, `uptimeS`, and `byQuery` (hits, misses, shared, upstream, and long per operation name).
- Environment: `STARTGG_CLIENT_ID`, `STARTGG_CLIENT_SECRET`, `STARTGG_REDIRECT_URI`, `STARTGG_SITE_TOKEN`, `SESSIONS_FILE` (on a writable volume); the full list is at the top of `proxy-server.js`. Needs Node 22.18+.

## Background loading of other phases

Once the bracket view has drawn a phase, `PhasePrefetch` (`src/app/services/phase-prefetch.ts`) loads the event's other phases in the background through the same `StartggService` calls (`background(lane)`), so opening one asks start.gg nothing. `StartggService` keeps every phase loaded, shown or background (`getLoadedPhases()`, for what needs every phase, like Show Projected across phases), and reuses it for 30 minutes if start.gg calls the phase `COMPLETED`, otherwise 30 seconds (the server keeps live sets 15 s). Which phases and the hard limits are in `phase-prefetch-plan.ts` (tested by `e2e/prefetch-plan.mjs`): logged in, every phase, cheapest first (Top 8 before pools), at most 40 phases, 120 requests per event, and 40 a minute; logged out, only phases whose sets fit in one or two requests, at most 6 phases, 15 requests, and 15 a minute. `RequestGate` runs background requests 2 at a time, only when none of the visitor's own are waiting, and leaves 20 a minute for them. Nothing loads while the tab is hidden, a page is loading, or on Save-Data. The first busy (503 `SITE_BUSY`), rate-limited (429), or failed answer stops it, never retried, and no new background loading starts for 5 minutes after a busy one. Background requests carry `x-bgg-background: 1`; `e2e/api-calls.mjs` logs them apart (`background`) and can refuse them (`backgroundRespond: busy`).

## Themes

- Dark is the default; `<html data-theme="light">` is the light theme. `src/index.html` sets it from localStorage (`bgg-theme`) before the first paint, `src/app/services/theme.service.ts` after that.
- Every color is a token in `src/styles/_tokens.scss`, with a dark and a light value. Components use `var(--name)`, never a color of their own. Material's colors for both themes are in `src/styles/_material.scss`.
- `e2e/screenshots.mjs` takes every page in both themes.
- The tournament page's styles are unscoped (`ViewEncapsulation.None`, everything under `.tp-page`) and its layout follows its own width with container queries, since the menu takes 250px beside it. Its text is in Archivo (`src/index.html`).

## Set dialog video

A set's YouTube `vodUrl` shows as a thumbnail (`i.ytimg.com`); a tap loads YouTube's player from `www.youtube-nocookie.com`, the only frame the Content-Security-Policy allows (`server/http-security.js`). Any other web link is an "Open video" link.

## Phone sheets

On a phone the set dialog and the attendee dialog are sheets from the bottom of the screen, and both drag down to close through one host directive, `SheetDragDirective` (`src/app/components/sheet-drag/`). A dialog is a sheet where its panel has `--sheet-drag: 1` (`src/styles.scss`). A downward drag moves the sheet when it starts on a `data-sheet-handle` element (the set dialog's head) or while the content under the finger is scrolled to its top; released past a quarter of the sheet's height, or flicked, it closes. The directive stops (`preventDefault`) every touch move that would otherwise reach the page, since Safari pulls to refresh on those. `e2e/touch-drag.mjs` has the finger drags the tests use.

## Characters on a set card

A bracket card's character column is 28px wide whatever a side played (`src/app/components/event/set-characters.ts`). A side with one character has one 18px icon. A side with more (a switch, a doubles team, or both) has two 12 to 16px icons on a diagonal and a "+N" for the rest. The lineup is the group of characters used in the most games, and the earliest group wins a tie. start.gg leaves a selection's `participant` empty in doubles, so a team's icons follow start.gg's order, not the names'.

## Pictures on a set card

A bracket card's picture column is 28px wide too. A single player has one 18px picture. A team (an entrant with two or more participants) has its first two players' pictures at 15px on a diagonal, the second in front with a circle cut out of the first behind it (`teamPictures` in `event.component.ts`, `.set-pictures` in its styles). They follow the order of the team's name (`inNameOrder` in `src/app/services/team-order.ts`), since start.gg can list the participants in another order. A teammate without a picture shows their initial on their own color: the player start.gg lists first keeps the team's color, which the search and the set dialog use. The pictures come from `phaseEntrantsQuery`, which already asks for every participant's `gamerTag` and profile picture (5 objects per two-player team: Port Priority DX Melee Doubles' 104 teams cost 521, measured 2026-11-15). A team's name starts 3px into its row (`.set-name-team`), so it sits 5px from the pictures, the gap a pair of characters leaves on its right; the row's width doesn't change. When the players' list fails to load, a team falls back to one initial, like a single player.

The tournament page's top 3s and Results show a team as the event overview's standings do (`players` in `toRow`, `.avs` in the page's styles): its first two players' pictures side by side at a single picture's size, in the order of its name, the first in front and the second tucked a third under it with a circle cut out around the first. The champions' pictures each have the gold ring inside their edge. A teammate without a picture has their initial on the page's avatar color.

## Building and testing

CI (`.github/workflows/ci.yml`, `e2e/compare.sh`) builds and tests every PR and push to main, in four jobs side by side: `build-and-e2e` (this branch's build and tests; the check the ruleset requires), `main` (the base branch's build through the same tests, as a report), `visual` (both builds' screenshots compared), and `live` (the checks against the real start.gg, then a walk through real brackets). Each uploads its own `e2e-out-<part>` artifact. Only `live` uses the start.gg token: two jobs using it at once tripped start.gg's rate limit (2026-11-15). A newer run for a PR cancels the older one. `e2e/api-calls.mjs` runs the app against a fake start.gg (`e2e/attendees.mjs` holds the Attendees page's part of it, `e2e/tournament-page.mjs` the tournament page's, which also saves the whole page in both themes to `e2e-out/tournament-page/`). `e2e/gql-cache.mjs` tests the cache, allowlist and site gate; `e2e/auth.mjs` runs the real server against a fake start.gg for login, sessions and security headers. `e2e/live-bracket.mjs` walks real Genesis X brackets in a browser for the progression tags and saves dark-theme screenshots to the `e2e-out-live` artifact (`live-bracket/`); it reports and never fails a run.
